## Целевая конфигурация

- Отдельный Compose project `ufifeed`; предполагаемый каталог `/home/ufian/ufifeed`, сейчас не создавался.
- Один контейнер приложения, без публикации портов. Telegram-команды — long polling, чтение — исходящее соединение MTProto. Домен, reverse proxy и внешний webhook не требуются.
- Постоянные bind mounts `./data:/app/data` и `./secrets:/app/secrets`. Конфигурация только для чтения. БД и сессия переживают пересборку образа.
- Непривилегированный пользователь контейнера с UID/GID 1000, каталоги данных и секретов доступны только владельцу. `read_only` root filesystem, writable `/tmp` через tmpfs, `cap_drop: ALL`, `no-new-privileges`.
- Один экземпляр приложения на Telegram session и один long-polling consumer на токен бота. Одновременный запуск авторизации и основного процесса с одним session-файлом не допускается.
- `restart: unless-stopped`, корректная обработка SIGTERM и ограничение времени остановки. Не использовать host network, privileged mode и Docker socket внутри контейнера.
- Начальный бюджет контейнера: до 1 GiB RAM и 1 CPU, затем скорректировать по замерам. Исходный текстовый объём ограничивать сроком хранения и лимитами импорта.
- Логи в stdout/stderr, Docker rotation, без message text, телефона, токенов и session strings. HTTP-логи нужно редактировать: токен Bot API присутствует в URL запроса.

Отдельная БД-контейнер для SQLite не нужна. Если позже появится PostgreSQL, готовность БД задавать через healthcheck + `depends_on: condition: service_healthy`, а повторные подключения обрабатывать в приложении: [документация Compose](https://docs.docker.com/compose/how-tos/startup-order/).

Compose-файл и Dockerfile нужно добавить вместе с работающим приложением. Сейчас фиктивного образа и неработающей команды `up` в репозитории нет.

## Секреты и первый запуск

Планируемые секреты: Telegram `api_id`, `api_hash`, bot token; session хранится отдельным файлом. Для будущего AI-режима отдельно понадобятся credentials провайдера. Не копировать секреты в image build context, аргументы CLI и Git. Файл секретов на VM — с правами `0600`; добавление в `.gitignore` само по себе не ограничивает доступ на сервере.

Последовательность после реализации:

1. Доставить код конкретного коммита на VM и собрать образ с меткой этого коммита. Если VM не имеет ключа GitHub, передать рабочее дерево без `.git` и секретов по SSH; не копировать личный SSH-ключ на сервер.
2. Создать каталоги данных/секретов, записать credentials локально на VM. Проверить права с UID контейнера и исходящие подключения.
3. Однократно запустить предусмотренную CLI-команду авторизации через `docker compose run --rm` в интерактивном терминале. Ввести код/2FA непосредственно там. Команду и имя сервиса определить при реализации.
4. Запустить миграции и приложение, проверить `/status`, выполнить `/start` владельцем, добавить несколько источников, получить ручную подборку.
5. Включить реальное расписание после подтверждения времени и часового пояса. Проверить один плановый запуск и один рестарт контейнера.

Это план, не команды для существующего CLI: реализация ещё не добавлена.

## Health и наблюдение

Healthcheck должен читать состояние приложения: heartbeat event loop, доступность SQLite, состояние задач collector/scheduler/delivery. Для тихого канала отсутствие новых сообщений не означает поломку; отдельно хранить время последней успешной сверки. При FloodWait показывать время окончания паузы. При отозванной сессии — `reauth_required`.

Следить за размером БД/диска, длительностью синхронизации, backlog доставки, возрастом последнего успешного run и ошибками доступа. Проверка Docker health сама по себе не перезапускает unhealthy-контейнер; временную недоступность Telegram следует пережидать, а зависшую критическую задачу — обнаруживать внутри приложения и завершать процесс с ошибкой для restart policy.

## Резервные копии и обновления

- Перед изменением схемы остановить приложение и сделать согласованную копию БД и session. Для online-backup SQLite использовать backup API, а не копировать только `.db` при активном WAL. Копия сессии также содержит credentials.
- Копии шифровать и хранить вне VM с ограничением доступа; предлагаемый срок 7 дней. Провести пробное восстановление в отдельный каталог. Истёкшие копии удалять, иначе retention приложения не удаляет данные из backup.
- Для обновления остановить единственный экземпляр, сохранить backup, выполнить миграции и запустить образ конкретного коммита. Откат образа допустим только при совместимой схеме; иначе восстановить согласованную копию вместе с соответствующей версией приложения.
- Не выполнять `docker compose down -v`, глобальный prune или перезапуск Docker ради обновления ufifeed: на VM работают другие проекты.
- После аварийного восстановления outbox может быть старее фактических отправок. Не повторять автоматически неопределённые доставки; проверить их с владельцем.
